# 模块一 · 消融穿越类型学

**Module 1 · A Typology of Ablation Traversals**

**版本**：v0.3（草案）｜ **依赖**：第 0 篇《命名论文》术语系统 ｜ **性质**：消融带研究的语法——一切后续设计（模块二）与测量（模块三）都建立在本类型学之上。

> **题解（概念谱系）**。"消融面"与"穿越类型学"之名，源自叙事哲学与符号学中的同名理论框架：该框架以**世界边界的消融深度**为标准，将虚构穿越叙事分为浅层消融、主体消融、双边消融、全域消融四级；其核心命题——"穿越的本质不是主体的空间位移，而是边界的本体消融与存在的重构"——正是本研究"消融带"概念的远源。本模块将这对概念从叙事世界之间移植到 LLM—Harness—人三体之间：前者分析虚构文本中的世界互渗，后者刻画智能系统中三个本体的互相穿越。为标明谱系、亦为切割论域，本模块定名《消融穿越类型学》。

---

## 摘要 / Abstract

本文对消融带（Ablation Zone）上的基本事件——穿越（traversal）——进行完整枚举与分类。三个本体（会生产的 LLM、会代谢的 Harness、会拍板的人）之间存在六条有向穿越路径；本文逐一给出定义、实例与现状诊断，并提出核心发现：六条路径中五条已被高度工程化，唯有**具名签署流**（attestation flow，人→LLM 的裁决路径）最稀薄、最无仪表，因而最有研究增量。本文进一步给出消融事件的判据（蒸发 evaporation 与年轮 growth rings 的分界）与穿越事件的最小数据结构（TraversalEvent）。

**关键词**：具名智能（Onymous Intelligence）；消融穿越（ablation traversal）；六路径（six flows）；具名签署流（attestation flow）；蒸发（evaporation）；年轮（growth rings）；形式化（formalization）

## 第一命题 · 具名智能 Onymous Intelligence（总纲与本篇分工）

**总纲复述**（第 0 篇命题 0.1）：存在一种智能形态，其标志是每一个产生后果的动作都可归属于一个具名的裁决者——生产的可以匿名（anonymous），代谢的可以匿名，生效的必须具名（onymous）。

**本篇分工**：为具名智能提供**语法**（grammar）。具名智能不是单一流的存在，而是六条穿越路径的耦合。类型学回答三个语法问题：具名智能由哪些穿越构成（第 2 节六路径）、哪条流是其命脉（命题 2.7：具名签署流）、哪些穿越算数（第 3 节年轮化判据）。没有语法，具名智能只是口号；有了语法，它才可枚举、可诊断、可形式化（第 5 节）。

## 1. 穿越事件

**定义 1.1（穿越，traversal）**。一个本体穿过另一个本体的事件。一次穿越携带三要素：

- **方向**（direction）：谁穿过谁（有向）；
- **载体**（carrier）：穿越的内容形态（输出、裁决、状态、装配、配置、呈现）；
- **留痕**（trace）：穿越之后是否留下持久结构。

**定义 1.2（经过与穿越的区分，passage vs. traversal）**。不携带留痕的穿过称为**经过**（passage，即蒸发 evaporation），携带留痕的穿过才是完整意义的穿越。日常用语中二者混称"穿越"，测量时必须区分（见第 3 节）。

**注 1.3（与叙事穿越的论域切分）**。叙事本体论的穿越类型学以"消融深度"分级（浅层／主体／双边／全域）；本类型学以**方向与留痕**分级（六路径 × 蒸发/年轮）。前者问"边界消融到何种本体深度"，本研究问"哪次穿越留下了年轮"——同一"消融"直觉，两个论域，两套仪表，互不隶属。

## 2. 三体六路径（Six Flows）

三个本体构成 3×2=6 条有向路径。逐一立档：

### 2.1 LLM → 人：生成流（generation flow）

- **定义**：模型的输出抵达人的感知（被阅读、被观看、被听取）。
- **实例**：回答、代码、图表、摘要。
- **现状**：工程化程度最高——流式输出、排版、多端同步。但该流的终点（人的裁决）被系统视为黑箱：系统知道"已送达"，不知道"被如何判定"。

### 2.2 人 → LLM：具名签署流（attestation flow）

- **定义**：人的裁决（adjudication）进入系统，被编译、收敛、清算（入账，ledgering）。
- **实例**：批准／驳回一段代码、签发一份报告、否决一次操作建议。
- **现状**：**全图最稀薄的一条**。现有系统把裁决压成一次点击（Approve/Reject），既无填单（判什么、依据什么、押上什么），也无入账（裁决去哪了），更无对账（事后如何回放）。本文第 4 节专题展开。

**辨析 2.2.1（指令流不是裁决流）**。提示词（prompt）是人→LLM 的另一子流，但它是**指令流**（instruction flow）——发起生产，而非**裁决流**——收敛生产。指令可撤销、可重发、无 stake；裁决不可撤销、有 stake。二者不得混同。

### 2.3 LLM → Harness：状态流（state flow）

- **定义**：模型调用的结果写入 Harness 的状态（文件、数据库、外部 API、记忆）。
- **实例**：工具调用、代码执行、写入工作区。
- **现状**：工程化成熟（工具调用协议、沙箱），但状态流的**裁决前置**（pre-adjudication）几乎不存在——大多数状态写入在无人裁决的情况下直接生效。

### 2.4 Harness → LLM：装配流（assembly flow）

- **定义**：Harness 为模型组装上下文（系统提示、记忆、检索、插件注入）。
- **实例**：上下文窗口的编排、技能加载。
- **现状**：工程化成熟且是 Harness 研究的主战场。但装配对人不可见——人不知道自己裁决的输出是在什么装配下生产的。

### 2.5 人 → Harness：配置流（configuration flow）

- **定义**：人对 Harness 的设置与改造（安装插件、调整偏好、编写技能）。
- **实例**：插件配置、长期指令。
- **现状**：中等工程化。配置流是慢变量，一次配置影响此后全部穿越，却几乎不被记录为"具名事件"（onymous event）。

### 2.6 Harness → 人：呈现流（presentation flow）

- **定义**：Harness 向人渲染界面与状态（界面、通知、仪表）。
- **实例**：聊天窗、日志、仪表盘。
- **现状**：工程化程度最高（前端技术栈全部服务于它），但呈现流普遍不携带**裁决所需结构**——它呈现"发生了什么"，不呈现"需要你判什么、你判了之后会怎样"。

**命题 2.7（全图观察）**。六条路径中，生成流、状态流、装配流、配置流、呈现流均已被工程系统重度覆盖；唯独具名签署流——唯一携带**不可撤销性**（irrevocability）与 **stake** 的流——处于无设施、无记录、无仪表的状态。**它是最稀薄的一条，也是唯一能让其他五条产生意义的一条**：没有裁决流，生产无人收敛、状态无人负责、装配无人校准、配置无人认领、呈现无人验收。

## 3. 消融事件：蒸发与年轮

**定义 3.1（消融事件，ablation event）**。一次穿越中发生相变的部分：穿越之后，至少一方的结构发生持久改变。

**定义 3.2（蒸发的三种形态，three orders of evaporation）**。以生成流→裁决流为例，蒸发有三阶：

1. **一阶蒸发**：输出未被阅读（生成流空转）；
2. **二阶蒸发**：输出被阅读但未被裁决（人看过，没拍板）；
3. **三阶蒸发**：裁决发生但未入账（拍了板，系统没记账，或被默认通过冒签 forged attestation）。

三阶蒸发是当前系统的默认结局，也是坏账（bad debt）的主要来源。

**定义 3.3（年轮化判据，ring-forming criteria）**。一次穿越留下年轮（growth rings），当且仅当满足：

1. **留痕**（traced）：穿越事件被记录（谁、何时、判什么、依据什么）；
2. **归属**（attributed）：痕迹记在具体名字下（具名三判据满足）；
3. **可引**（citable）：该痕迹能被后续穿越引用（成为装配流、配置流或下一次裁决的输入）。

三条缺一，即为蒸发。年轮化判据是模块三《年轮测量学》的测量原点。

## 4. 具名签署流专题（The Attestation Flow）

### 4.1 子类型枚举

具名签署流不是单一流，而是一个流族：

| 子流 | English | 定义 | 性质 |
|---|---|---|---|
| 签署 | attestation | 具名者判定通过并入账 | 正常流 |
| 拒签 | declined attestation | 具名者判定否决并入账 | 正常流（否决也是资产） |
| 退单 | chargeback | 具名者退回，要求补充后重裁 | 正常流（柜台成本显化的途径） |
| 补签 | retroactive attestation | 事后追认已生效的状态 | 风险流（须标记时效与正当性） |
| 会签 | countersignature | 多具名者共同裁决 | 扩展流（群体裁决的最小单元） |
| 冒签／代签 | forged attestation | 系统以人名义默认通过 | **伪流**——坏账的极端形态 |

### 4.2 稀薄性的机制诊断

具名签署流为何最稀薄？三个机制：

1. **压扁**（flattening）：界面把裁决压成一次点击，裁决的声明结构（判什么、依据、押上什么）无处填写；
2. **截流**（interception）：系统以"自动化""默认通过""推荐即生效"截走裁决，具名者甚至不知道有裁决待作；
3. **蒸发**（evaporation）：即使裁决发生，系统不记账，裁决无法被后续穿越引用，具名者体会不到自己的 stake 产生了复利。

### 4.3 增量论证

研究增量的排序原则：投在六路径中边际收益最大处。五条路径的工程化已饱和，具名签署流接近空白；且由命题 2.7，它是其余五流的意义收敛点。故消融带研究的第一对象即具名签署流，其实施载体为具名柜台（Attestation Counter，模块二），其测量仪表为年轮（growth rings，模块三）。

## 5. 形式化：穿越事件的最小数据结构（TraversalEvent）

为后续仪表与原型实现，定义穿越事件的记录格式：

```
TraversalEvent = {
  id:            事件唯一标识（event id）
  direction:     ∈ {生成流 generation, 具名签署流 attestation, 状态流 state,
                    装配流 assembly, 配置流 configuration, 呈现流 presentation}
  subtype:       ∈ {签署 attested, 拒签 declined, 退单 chargeback, 补签 retroactive,
                    会签 countersigned, 冒签 forged, …}   // 仅具名签署流使用
  carrier:       载体引用（输出/裁决单/状态写入/…）
  signer:        具名者标识（具名签署流必填，其余流可空）
  stake:         押注声明（判什么、依据什么、押上什么）
  revocable:     布尔，是否可撤销
  ledger_state:  ∈ {挂账 pending, 已入账 ledgered, 已退单 returned, 坏账 bad_debt}
  ring_refs:     引用本事件的后续穿越列表（年轮深度的原始数据）
  timestamp:     时间戳
}
```

**状态机**（ledger_state machine）：具名签署流的 ledger_state 迁移为 `挂账 →（签署|拒签）→ 已入账`、`挂账 → 退单 → 挂账'`、`已入账 →（审计发现伪造）→ 坏账`。冒签的定义即：无 signer 与 stake 而 ledger_state 为已入账的记录——形式化使"坏账"成为可计算的字段而非修辞。

## 6. 开放问题

1. **第四本体问题**：机构、资本平台是否构成第四个本体，在穿越中隐身？若成立，六路径将扩展为十二路径。
2. **穿越的嵌套**（nested traversal）：一次穿越可否以另一次穿越为载体（如裁决一段"由裁决生成的"内容）？嵌套深度是否需要上限？
3. **群体穿越**：会签（countersignature）的最小协议——先后签、并行签、加权签——哪种结构既保具名又防责任稀释？
4. **配置流的具名化**：慢变量（插件、技能、长期指令）是否也应要求具名签署？其 stake 如何计价？
5. **跨论域回译**：叙事消融四级矩阵（浅层／主体／双边／全域）能否回译为三体穿越的"消融深度"仪表？若可，六路径类型学将获得第二根分类轴（方向 × 深度）。
